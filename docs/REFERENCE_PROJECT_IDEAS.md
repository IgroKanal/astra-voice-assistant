# Идеи по мотивам открытых голосовых ассистентов

Дата обзора: 2026-11-14.

Здесь зафиксированы только общие продуктовые и архитектурные идеи. Исходный код, структуру файлов, формулировки команд, оформление и ресурсы сторонних проектов в Astra не переносили.

## Источники

- [RustamovAkrom/JARVIS](https://github.com/RustamovAkrom/JARVIS) — Windows-ассистент с отдельными слоями распознавания, wake word, маршрутизации команд и действий; в README также описаны быстрые офлайн-команды и дополнительный AI-режим.
- [RustamovAkrom/Voices-Assistant-For-Windows](https://github.com/RustamovAkrom/Voices-Assistant-For-Windows) — пример модульного разделения распознавателя, синтеза речи, исполнительного контура и навыков; описание проекта показывает гибридные варианты STT/TTS и каталог примеров команд.

Оценка основана на публичных README и описаниях репозиториев. Это не аудит их исходников, безопасности, качества речи или реальной задержки.

## Что подходит Astra

1. **Разделять быстрые команды и разговорный ИИ.** Частые локальные действия должны отвечать без сетевого запроса; модель нужна для открытых вопросов и только в пределах явно выбранного провайдера. В Astra уже есть такой базовый принцип; его стоит закреплять тестами задержки и запрета нежелательного cloud fallback.
2. **Развивать навыки как явные модули.** Для каждого навыка полезны описание, типизированные входы, требуемые разрешения, предел времени, отмена и понятный результат. Регистрация действий должна оставаться статической и проходить общий ActionPolicy; текст команды или конфигурация не должны вызывать Python-функции по произвольной строке.
3. **Сохранять заменяемость STT и TTS.** Движки распознавания и голоса можно сравнивать за общими интерфейсами по задержке, точности русского языка, звучанию, офлайн-работе и приватности. Новый движок добавлять после измерений и проверки лицензии/размера, без автоматической загрузки крупных моделей.
4. **Делать состояния ассистента наблюдаемыми.** Слушает ли Astra, распознаёт ли запрос, выполняет ли действие или ждёт ответ — эти состояния должны иметь однозначные события и конечные тайм-ауты. Отладочные метрики не должны сохранять распознанный текст и содержимое файлов.
5. **Поддерживать расширяемость через проверяемые описания.** Будущий каталог навыков может перечислять только заранее зарегистрированные типы действий, их аргументы и разрешения. Не загружать сторонние плагины автоматически и не исполнять YAML/Python как код.

## Что не переносить в Astra

- Свободное отображение произвольного текста на имя Python-действия.
- Команды выключения, перезагрузки, блокировки и любые необратимые операции без отдельной политики, подтверждения и проверок.
- Обязательные внешние ключи wake-word/облачного AI в конфигурации или исходниках.
- Автоматическую загрузку моделей при запуске, неограниченное прослушивание или скрытую передачу текста облачному провайдеру.
- Зависимости и модельные файлы только ради совпадения с демо другого проекта.

## Очерёдность для дорожной карты Astra

1. Завершить пользовательскую проверку реального микрофона, голоса и времени от wake-фразы до первого слышимого ответа; автоматические тесты этого не заменяют.
2. На реальных установленных движках сравнить доступные голоса и задержки, не скачивая модели; записать методику и p50/p95 отдельно для STT, LLM и TTS.
3. На основе результата улучшать текущие провайдерные интерфейсы, отмену и быстрый локальный путь; каждый новый навык подключать через статическую типизированную регистрацию и общую политику разрешений.

Ни один пункт этого обзора сам по себе не означает, что сторонний проект прошёл независимую проверку или что его функция уже реализована в Astra.
